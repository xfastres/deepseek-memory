> **状态：设计方案，尚未实施。**\
> **版本日期：2026-10-28**\
> **前置方案：dsh-memory v2「可信的个人记忆系统」**\

> 自动提取与判断、策略控制写入、用户随时查看和纠错"。**

本文区分三类信息： - **已核实**：来自既有调查记录或已有实现情况。 -
**待验证**：必须通过最小实验确认，不能假设接口一定可用。 -

## 1. 产品目标与设计原则

dsh-memory 不是聊天总结工具，而是为 DSH
提供可追溯、可更新、可纠正、可安全遗忘的长期记忆能力。

系统应满足以下原则：

1.  **自动维护**：用户正常对话即可触发记忆提取，不要求用户手工整理每一条记忆。
2.  **证据优先**：正式记忆必须有来源证据，结论强度不得超过证据支持程度。
3.  **分级写入**：低风险、高置信度、证据充分的变化可以按策略自动写入；不确定、冲突或高风险内容进入待处理状态。
4.  **用户可纠正**：用户可以查看、质疑、让 LLM
    修改、手动编辑、合并、撤回或删除记忆。
5.  **异议优先处理**：用户明确指出记忆错误后，系统应立即阻止该错误内容继续参与普通检索和注入；正式版本变更可以在核查后完成。
6.  **变更可解释**：每次变更都说明变更前后、原因、证据和执行方式。
7.  **历史可追溯**：正式记忆的变更写入
    Git；旧版本保留不代表旧版本仍可被正常使用。
8.  **失败不影响对话**：提取、检索或记忆存储失败不得导致 DSH
    主对话不可用。
9.  **最小化记忆**：不保存无长期价值的闲聊；敏感信息默认不自动进入可注入记忆。
10.  **逐步交付**：先做可见、可理解、可验证的最小闭环，再增加
     L2/L3、复杂检索和自动化。

### 1.1 可验收的系统属性

------------------------------------------------------------------------------------------------

  属性                                验收标准

----------------------------------- ------------------------------------------------------------

  可信                                正式记忆可追溯到会话、事件和证据；证据不足时不会伪装成事实

  自动化                              后台能从完成的对话中生成候选，并按策略分类处理

  可控                                用户可以查看、纠正、编辑、撤回、删除；AI
                                      不能代替用户执行授权操作

  有用                                新对话自动检索相关记忆；评估集前 5 条召回率达到设定目标

  安静                                无关、撤回、被用户否定、越权或敏感记忆不会被正常注入

  可解释                              每次变更和每次注入都能解释原因并显示证据

  可演进                              新旧事实有版本与有效期，纠错后旧版本不再参与正常检索

  可迁移                              正式记忆有 Git 历史；SQLite 索引可重建；数据可导出
  ------------------------------------------------------------------------------------------------

## 2. 已知实现基础与边界

### 2.1 已有的持久化通道调查

既有调查记录显示，本机任务板插件 `@linxin666/dsh-client-ui-task-board`
使用：

-   Host 端 `ctx.webServer.register(route)` 注册 `/api/...` 路由；
-   Client 端通过同源 `fetch()` 调用；
-   请求受回环地址、同源标记或 Host 浏览器认证 Cookie 约束；
-   不能假设自定义 Remote 命名空间可用，既往 `remote.memoryConversation`
    曾导致启动失败。

因此，优先采用 Host HTTP 路由，但仍必须先完成最小 ping 实验。

### 2.2 已有 Git 账本 Provider

既有调查记录显示，`packages/provider-git-ledger` 已实现并有 31
项测试通过，包含：

-   正式记忆存于 Git，每次变更生成提交；
-   `ADD / UPDATE / RETRACT / SUPERSEDE` 变更提案；
-   基线版本冲突检查与仓库锁；
-   SQLite FTS5 trigram 检索与 BM25；
-   索引可从 Git 重建；
-   撤回的记忆不会进入正常检索，但历史保留。

本方案应复用 Provider，不在 Client 中重新实现 Git
或索引逻辑。**测试通过不等于已集成进 DSH 插件；集成状态需要单独验证。**

### 2.3 DSH 接口边界

既有调查记录显示：

-   `ctx.systemPrompt.context({ name, order, text })` 可注册动态上下文；
-   `ctx.tools.register()` 可注册 AI 工具；
-   `agent.inject()` 在插件规范中有说明，但实际调用链仍需验证；
-   `systemPrompt.context`
    回调可能拿不到当前用户消息，需实验确认可读取当前轮消息的钩子；
-   不应向 DSH
    会话日志写入自定义事件类型，插件自己的状态存放在插件数据域；
-   批准、确认等授权操作必须由用户执行，不能由 AI 工具代劳。

``` text

        │
        ├──────────────► Memory Extractor（异步提取）
        │                         │
        │                         ▼
        │                结构化候选 / 变更提案
        │                         │
        │                         ▼
        │                Evidence Validator
        │                         │
        │                         ▼
        │                 Memory Policy
        │            ┌────────────┼─────────────┐
        │            ▼            ▼             ▼
        │        自动接受      待用户处理       拒绝/忽略
        │            │            │
        │            └──────┬─────┘
        │                   ▼
        │              Memory Writer
        │        版本检查 / 冲突检查 / 权限检查
        │                   │
        │                   ▼
        │              Git Ledger
        │                   │
        │            ┌──────┴──────┐
        │            ▼             ▼
        │       SQLite FTS      Change Journal
        │            │             │
        │            ▼             ▼
        │       Retriever      记忆管理 UI
        │            │       查看 / 异议 / 修改 / 删除
        │            ▼
        │      Context Injection
        │            │
        ▼            ▼
     用户正常对话 ◄── DSH Agent
```

### 3.1 职责分离

-----------------------------------------------------------------------------------------------------

  组件                    职责                                           禁止事项

----------------------- ---------------------------------------------- ------------------------------

  L0 会话日志             提供原始证据，只读                             不改写原始会话

  Memory Extractor        识别候选、判断新增/修改/合并/冲突              不直接写正式记忆

  Evidence Validator      校验来源、事件位置、原文哈希和证据类型         不把模型猜测当作证据

  Memory Policy           决定自动接受、待处理或拒绝                     不绕过敏感性、权限和冲突规则

  Memory Writer           执行已获准的变更、版本检查和提交               不自行决定语义是否正确

  Git Ledger              保存正式记忆与正式版本历史                     不承担高频运行时队列

  SQLite 运行时库         保存候选队列、异议状态、注入记录、设置和反馈   不作为正式记忆唯一事实源

  Retriever               按当前问题、范围、状态和预算检索               不返回已撤回或已否定的记忆

  Client UI               展示证据与状态，发起用户操作                   不直接写 Git 文件

  AI Tools                搜索和提交变更提案                             不批准自己的提案，不绕过

                                                                         Writer
  -----------------------------------------------------------------------------------------------------

## 4. 记忆模型

### 4.1 L0：原始会话层

-   使用 DSH 原有会话日志作为证据源；
-   原始记录只读；
-   记忆记录保存会话 ID、事件序号、说话方和原文哈希；
-   不把完整会话复制进正式记忆库；
-   如果原始证据不可访问，候选应标记证据缺失，不能伪造引用。

### 4.2 L1：记忆原子

L1 是最小的正式记忆单元。建议字段：

``` ts
type MemoryStatus =
  | "active"
  | "review_pending"
  | "superseded"
  | "retracted";

type MemoryType =
  | "preference"
  | "fact"
  | "goal"
  | "event"
  | "decision"
  | "constraint"
  | "open_loop"
  | "hypothesis";

interface MemoryRecord {
  memory_id: string;
  version: number;
  status: MemoryStatus;
  type: MemoryType;
  content: string;
  scope: {
    kind: "global" | "workspace" | "project";
    id?: string;
  };
  evidence: Array<{
    session_id: string;
    event_seq: number;
    role: string;
    quote_sha256: string;
  }>;
  source_kind:
    | "user_explicit"
    | "user_correction"
    | "session_extraction"
    | "agent_inference";
  confidence: number;
  importance: number;
  valid_from?: string;
  valid_to?: string;
  supersedes_id?: string;
  superseded_by_id?: string;
  sensitivity: "normal" | "private";
  pinned: boolean;
}
```

字段命名可根据现有 Provider schema
调整，不应为了照抄此示例而破坏已有兼容性。

### 4.3 运行时状态与变更日志

候选队列、用户异议、自动写入决策、注入记录和使用反馈属于高频运行时数据，放在
SQLite 或经阶段 2.3 验证后的 `storageDomain` 中。

每个变更事件建议记录：

-   `change_id`、`memory_id`、基线版本；
-   操作意图：`ADD / UPDATE / MERGE / RETRACT / SUPERSEDE / NO_CHANGE / CONFLICT / REJECT`；
-   提案内容、提案理由和证据引用；
-   策略判定及判定原因；
-   状态、创建时间、处理时间；
-   触发来源：自动提取、用户异议、用户手动编辑或 AI 工具；
-   最终执行结果与 Git commit 标识（若已提交）。

Change Journal 解释"为什么发生变化"；Git Ledger
保存正式内容历史。两者职责不同，不重复存储完整会话正文。

### 4.4 L2：场景记忆

L2 将相关 L1 原子组织为场景，例如"dsh-memory 项目""当前学习计划"。L2
必须引用 L1 ID，并可附用户可编辑的摘要。

L2 第一阶段不自动生成。待 L1 的自动提取、纠错和版本流程稳定后再做。

### 4.5 L3：长期画像

L3 仅从正式有效的 L1/L2 推导，例如稳定的沟通偏好或工作方式。

要求： - 每条画像结论都能回溯到支撑它的 L1/L2； -
画像不能比证据更绝对； - 支撑记忆被撤回、修改或否定时，相关画像自动进入
`review_pending`； - L3 不得把推断伪装成用户原话； - L3
的自动生成后置，不属于第一版 MVP。

## 5. 证据、置信度与记忆写入策略

### 5.1 证据规则

-------------------------------------------------------------------------------------------

  类型                    最低证据要求                           不能作为唯一依据

----------------------- -------------------------------------- ----------------------------

  preference（偏好）      至少一条用户原话明确表达偏好           仅凭 AI 回复或一次行为猜测

  goal（目标）            用户明确表达目标，且能确定其时间范围   AI 推断

  fact（事实）            用户原话、可靠工具结果或明确会话记录   无来源断言

  event（事件）           工具结果或会话中的明确记录             无证据

  decision（决定）        用户明确决定，或有可验证的执行记录     AI 提议但用户未同意

  constraint（约束）      用户明确提出或可验证的项目约束         推测

  hypothesis（假设）      可有推断来源，但必须明确标记为假设     不得伪装成事实，默认不注入
  -------------------------------------------------------------------------------------------

证据必须与记忆结论相匹配。证据中只出现"这次请画图"，不能直接推导成"用户在所有场景都偏好图示"。

### 5.2 自动写入分级

目标不是所有记忆都等用户审批，也不是所有模型判断都直接写入。采用分级策略：

-------------------------------------------------------------------------------------------------------------------------------------

  分类                    典型条件                                                 默认动作

----------------------- -------------------------------------------------------- ----------------------------------------------------

  低风险、高置信度        有直接证据、范围明确、无冲突、非敏感、与现有记忆不矛盾   可按策略自动写入

  中等确定性              证据存在但范围不明、是否长期有效不确定、疑似重复         进入候选队列，等待用户查看或系统后续补充证据

  明确冲突                与有效记忆矛盾，且无法用时间或作用范围解释               不覆盖；标记 `CONFLICT` 并请求用户判断

  敏感或高影响            私密个人信息、敏感推断或可能造成明显负面影响的画像       默认不自动保存或不自动注入；遵循明确的用户授权策略

  无长期价值              普通闲聊、一次性问题、短期任务细节                       忽略，不创建记忆

  证据不足                无法定位原始证据，或结论强度超出证据                     拒绝正式写入，保留原因用于诊断
  -------------------------------------------------------------------------------------------------------------------------------------

### 5.3 自动接受不是单纯依赖一个置信度分数

自动写入必须同时通过硬性门槛：

1.  证据校验通过；
2.  记忆类型允许自动写入；
3.  不是敏感或受限制内容；
4.  不存在未解决冲突；
5.  作用范围明确；
6.  没有针对该记忆的未处理用户异议；
7.  基线版本未发生并发变化；
8.  用户没有关闭自动记忆或对该类别禁用自动保存。

置信度是一个信号，不是安全授权。自动接受的阈值应通过评估集校准，不能在没有数据时宣称某个数值可靠。

### 5.4 自动记忆设置

至少提供： - 全局自动记忆开关； - 自动接受低风险记忆开关； -
按类型控制（偏好、项目事实、目标等）； - 私密记忆策略； -
暂停自动提取； - 候选静音或忽略某类建议。

默认行为应保守：自动提取可以先开启，正式自动接受按风险策略逐步启用；用户可随时关闭。

## 6. 记忆异议与纠错闭环

这是本次修订的核心功能。

### 6.1 用户可以通过多种方式发起异议

-   在记忆管理页面点击"有误 / 太宽泛 / 已过期 / 不该保存"；
-   对某条记忆输入自然语言异议；
-   在回答中标记"这条记忆不正确"；
-   直接说"把这条记忆改成......""这件事已经变了""删除这条记忆"。

系统必须把异议关联到具体 `memory_id`
和当前版本。若无法确定目标记忆，应先让用户选择，不得猜测并修改其他条目。

### 6.2 异议类型

建议先支持：

-   `incorrect`：内容不正确；
-   `too_broad`：范围过宽；
-   `outdated`：已经过期；
-   `missing_context`：缺少适用条件；
-   `wrong_scope`：作用范围错误；
-   `duplicate`：与其他记忆重复；
-   `should_not_store`：不应该保存；
-   `delete_request`：明确请求删除；
-   `other`：其他。

异议类型用于引导核查，不应机械决定最终操作。例如"太宽泛"并不等于整条记忆为假。

### 6.3 异议处理流程

``` text
用户提出异议
    │
    ▼
定位 memory_id + 当前版本
    │
    ▼
立即记录异议事件
    │
    ├─ 明确说“错误 / 不要再使用 / 删除”
    │       └─ 立即阻止该版本进入普通检索和注入
    │
    └─ 仅说“太宽泛 / 缺少上下文”
            └─ 标记 review_pending；按风险决定是否临时停止注入
    │
    ▼
读取原始证据与上下文
    │
    ▼
LLM 生成变更提案（不是直接写正式记忆）
    │
    ├─ 证据充分、低风险、无冲突
    │       └─ 按自动写入策略执行
    │
    ├─ 证据不足 / 范围不明确
    │       └─ 向用户询问或展示候选表述
    │
    ├─ 与其他记忆冲突
    │       └─ 保持冲突状态，请用户判断
    │
    └─ 用户明确要求删除
            └─ 进入撤回或彻底删除专门流程
    │
    ▼
Memory Writer 校验权限、基线版本与约束
    │
    ▼
Git 正式变更 + 索引更新 + Change Journal
    │
    ▼
验证旧错误内容不再被普通检索或注入
```

### 6.4 异议期间的使用规则

必须避免用户刚指出错误，系统下一轮仍然继续使用旧内容。

-   用户明确指出"错误""不要再用"时：立即把该版本加入运行时的抑制列表，普通检索和注入必须过滤；不能等
    Git 提交完成后才停止使用。
-   用户指出"太宽泛"时：先记录异议并进入
    `review_pending`。如果宽泛表述可能误导后续回答，临时停止注入；否则也不得在核查前把它当作已确认的新结论。
-   异议尚未解决的记忆不能被自动接受流程重新激活。
-   若存储服务暂时不可用，当前运行时仍应尽可能遵循本轮明确的纠错指令；持久化失败要向用户说明，不能声称已经永久修改。

### 6.5 LLM 修改与手动修改

用户可以选择：

1.  **让 LLM 修改**：LLM 基于原始证据提出新表述，并显示修改理由；
2.  **手动修改**：用户直接编辑内容；
3.  **确认建议**：用户确认某个候选版本；
4.  **合并**：将重复记忆合并，保留来源关联；
5.  **撤回**：停止使用，但保留历史；
6.  **彻底删除**：执行隐私删除流程，必须二次确认。

手动编辑也必须经过统一
Writer，不能绕过版本控制、证据关联和索引更新。用户编辑后的内容应标记
`source_kind=user_correction`，并记录用户修改事件；不能把用户新写的文本错误地归为原始对话中的旧原话。

### 6.6 异议示例：记忆太宽泛

原记忆：

> 用户偏好通过图示、请求流程和分步骤教程理解复杂技术架构。

用户异议：

> 描述太宽泛。

正确处理方式：

1.  记录 `too_broad` 异议，关联当前 memory ID 和版本；
2.  检索原始会话，检查用户是否明确表达过适用场景；
3.  如果证据只支持"理解陌生项目时希望看目录职责和请求---响应流程"，提案只能收窄到该证据范围；
4.  如果没有证据支持具体收窄方式，不能直接编造新内容，应询问用户或保留待处理状态；
5.  展示修改前、候选修改后、证据与理由；
6.  根据策略自动写入或等待用户确认；
7.  写入新版本后过滤旧版本，验证检索结果。

"用户说太宽泛"只说明范围需要重新检查，不代表用户认可任何特定的替代表述。

## 7. 写入链路与状态机

### 7.1 自动提取主链路

``` text
一轮对话结束
  → 异步提取候选
  → 证据验证
  → 与正式记忆和未决候选比较
  → 生成变更意图
  → Policy 决策
       ├─ AUTO_ACCEPT
       ├─ REVIEW_REQUIRED
       ├─ CONFLICT
       ├─ NO_CHANGE
       └─ REJECT
  → Memory Writer（仅执行允许的变更）
  → Git Commit
  → 更新索引
  → 写入 Change Journal
  → UI 更新状态
```

提取与写入必须异步执行，不能阻塞正常回复。后台失败应可重试且幂等，避免重复创建同一条记忆。

### 7.2 候选状态

候选队列建议使用独立状态，不与正式记忆状态混为一谈：

-   `proposed`：新候选；
-   `validating`：正在验证证据；
-   `review_pending`：等待用户处理；
-   `auto_accepted`：已按策略自动接受；
-   `accepted_by_user`：用户确认；
-   `rejected`：拒绝；
-   `conflict`：冲突待处理；
-   `no_change`：无需变化；
-   `failed`：处理失败，可重试。

正式记忆状态则保持简洁，例如
`active / superseded / retracted`。`review_pending`
可以同时是运行时的异议标记，但不能让普通检索把它误认为已确认的有效记忆。

### 7.3 变更操作语义

  操作          含义

------------- ----------------------------------------------

  `ADD`         创建新的正式记忆
  `UPDATE`      对同一记忆创建新版本
  `MERGE`       合并重复记忆并保留来源关联
  `SUPERSEDE`   新事实取代旧事实，旧版本记录有效期与替代关系
  `RETRACT`     撤回记忆，普通检索与注入停止使用
  `NO_CHANGE`   候选与现有记忆等价，不创建新版本
  `CONFLICT`    无法安全判断新旧关系，等待解决
  `REJECT`      证据、权限或策略不满足，拒绝写入

所有写入必须携带基线版本；基线已变化时重新比对，不能覆盖其他并发修改。

## 8. 正式记忆、异议与版本处理

### 8.1 Git 与 SQLite 分工

-   Git：正式记忆内容、正式版本和提交说明；
-   SQLite /
    `storageDomain`：候选队列、异议事件、自动决策记录、注入记录、使用反馈和索引；
-   FTS 索引可重建，不是正式记忆事实源；
-   UI 通过 Host API 操作，不直接改 Git 文件。

### 8.2 版本处理规则

-   正常修改：保留 `memory_id`，递增 `version`，旧版本标记
    `superseded`，建立新旧关联；
-   新事实取代旧事实：记录 `valid_to`、`superseded_by_id`；
-   合并：明确主记录与被合并记录的映射，保留全部来源；
-   撤回：更新正式状态，并立即从普通检索和注入中排除；
-   异议待处理：运行时先抑制不应再使用的版本；不必为每次临时状态都创建正式
    Git 版本；
-   自动接受：写入前再次检查基线版本、异议状态和策略条件；
-   索引更新失败：正式变更与索引状态要可恢复，提供重建机制，不能静默返回成功。

### 8.3 撤回与彻底删除

-   **撤回**：停止检索和注入，保留 Git 历史。
-   **彻底删除**：重写历史、移除相关正文，并处理索引、导出、日志和可控备份中的副本。操作前二次确认，明确告知不可撤销。
-   不能宣称重写 Git
    历史就自动删除了所有副本；备份和已导出数据需要单独定义清理范围。
-   `private` 记忆默认不注入普通对话，且不通过普通 AI 搜索工具暴露。

## 9. 检索与注入

### 9.1 第一版检索

优先使用现有 SQLite FTS5 trigram + BM25，不先引入向量检索。

候选排序可考虑： - 文本相关度； - 当前 scope 匹配； - 重要度； -
按记忆类型配置的新近度； - 用户反馈； - 置顶策略。

不要把所有因子简单相乘到可能让相关记忆得分趋近于零。先保留可解释的分项得分，再用评估集校准排序。

### 9.2 必须过滤的内容

普通检索与注入不得返回： - `retracted`； - 已被 `superseded`
的旧版本； - 有未解决且要求停止使用的用户异议； - `private`； -
默认不注入的 `hypothesis`； - 当前 scope 不匹配的项目记忆； -
用户已明确要求不要再使用的内容。

### 9.3 注入预算与可解释性

-   默认每轮最多 8 条、约 1200 个中文字，实际数值需用评估校准；
-   记录会话、轮次、memory ID、版本、分项得分和注入理由；
-   UI 能显示"本轮使用了哪些记忆、为什么使用"；
-   用户可标记有用、不相关或错误；
-   错误反馈立即触发异议/抑制流程，而不是只降低分数。

### 9.4 DSH 集成实验

先验证能够稳定获取当前用户消息的钩子，再实现按当前问题检索。候选方案为
`agent/pre-step` 或 `turn/start` + `agent.inject()`，均需实验确认。

## 13. 评估指标与测试用例

### 13.1 自动提取指标

-   候选精确率：生成的候选中，有多少确实值得记忆；
-   候选遗漏率：重要且有证据的信息是否经常漏掉；
-   自动接受正确率：自动写入的记忆有多少正确；
-   证据规则拦截率：证据不足或类型不匹配的候选是否被拦截；
-   用户纠错率与主要纠错原因；
-   重复候选率；
-   后台处理失败率与重复提交率。

### 13.2 检索指标

建立 20--50 条真实问题的初始评估集，标注应检索到的记忆： - 前 5
条召回率； - 误注入率； - 平均注入字数； -
被用户标记为错误或无关的比例； - 被撤回、被否定或 private
记忆的注入次数，目标为 0。

### 13.3 必须覆盖的异议测试

1.  用户说"这条记忆是错的"：该版本立即被抑制。
2.  用户说"太宽泛"：不自动编造替代内容。
3.  用户说"我现在已经改变想法"：核查时间和有效期，不能把旧事实静默覆盖。
4.  用户手动编辑时后台提取器同时更新：基线冲突被发现。
5.  Git 提交成功但索引更新失败：系统能够重试或重建索引。
6.  存储不可用：界面不谎称成功，主对话仍可继续。
7.  用户请求删除：撤回和彻底删除被清楚区分。
8.  画像的支撑原子被否定：相关 L3 句子被标记复核。
9.  用户关闭自动记忆：之后不再执行超出设置范围的自动写入。
10.  AI 尝试批准自己的提案：权限校验拒绝。

## 16. 明确暂不做的事情

在 L1 自动提取、自动写入策略和纠错闭环通过验收前，不做：

-   多用户与云同步；
-   把完整会话原文复制到记忆库；
-   AI 无约束直接写正式账本；
-   AI 代替用户执行批准、确认或不可逆删除；
-   无评估数据就加入向量检索；
-   修改 DSH 核心源码；
-   一开始就自动生成复杂 L2/L3 画像；
-   仅用单一置信度分数决定所有写入。

## 17. 当前建议的下一步

不要一次实现整套自动记忆。按以下顺序推进：

1.  **先完成阶段 2.1**：验证 Host HTTP 路由与 Client
    安全通信，确认插件失败不影响 DSH 启动。
2.  **完成阶段 2.4**：将现有界面正式变更统一接入
    `provider-git-ledger`，确保 Git 账本是正式记忆唯一事实源。
3.  **完成阶段
    3.6--3.7**：先实现记忆异议、立即抑制、手动编辑、版本差异与统一
    Writer。
4.  **实现阶段 4.1--4.4**：让 LLM
    自动提取并分类，但先在影子模式运行，比较提案与人工判断，不立即开启自动接受。
5.  **基于评估逐类开启自动接受**：从低风险、高证据强度的记忆类别开始；其余进入待处理队列。
6.  **最后实现 L2/L3**：确保上游 L1
    变化时，高层记忆可以被追溯和重新评估。

**MVP 完成定义：**
系统能从对话自动提出有证据的记忆变化；低风险内容可按策略自动保存；用户能查看来源、提出异议、让
LLM
修改或手动编辑；正式变化有版本历史；被明确否定或撤回的旧内容不会再被正常检索和注入；任何记忆功能失败都不会阻塞正常对话。
