# 阶段 4 设计：从原子记忆到场景与人设

这份文档回答一个问题：**L2 场景和 L3 人设，到底是「新数据」还是「视图」？**

答案决定了后面所有实现。我的结论是：**都是视图**，账本里的唯一事实仍然是 L1 原子记忆。

---

## 为什么不能是独立数据

用户的四层提案里，L2 是场景化的记忆（「这段时间我们在解决 X」），L3 是用户画像（「他偏好简洁、且坚持中文」）。

如果 L2/L3 是**独立存储的、需要维护的数据**，会立刻遇到三个问题：

1. **一致性**：撤销一条原子记忆之后，已经写好的场景摘要还提不提它？改摘要就要重写历史。
2. **不可解释**：用户看到「他偏好简洁」，但账本里找不到是哪句话支撑的——这正是当初定下「证据必须与结论匹配」要防的事。
3. **幻觉固化**：摘要一旦落库，错误就从「一次性的推断错误」变成了「永久事实」。

所以：**原子记忆是事实，场景与人设都是可重算的视图。** 随算随用，允许重建，删除视图不损失任何信息。

## L2 场景：结构先行，摘要可选

### 场景的构成

一条场景记录不是一段自由文本，而是：

```
id          场景 id
title       标题（用户可改）
members     成员原子记忆 id 列表（≥2）
evidence    成员证据的并集（session_id + event_seq）
period      [最早成员时间, 最晚成员时间]
summary     摘要文本（可选，见下）
origin      "user" | "model" | "structural"
```

### 什么时候成型

**结构信号**（不依赖模型，随时可算）：

- 同一会话内、同一 scope 下、7 天内产生 ≥3 条原子记忆；
- 或 ≥2 条原子记忆共享同一个 entity（`entities` 字段交集非空）。

结构信号只负责「这几条应该放一起看」，**不生成文案**。这类场景的 `summary` 为空，界面上显示「N 条相关记忆」加成员列表——没有摘要，但不会撒谎。

### 摘要从哪来

两条路，都要保留证据：

1. **用户写**：`origin: "user"`，最高权威，永不被自动流程覆盖。
2. **模型写**：`origin: "model"`，必须满足：
   - 输入的每条成员原子记忆都有可解析的证据；
   - 摘要里出现的每个具体事实，必须能在成员原文里找到对应（做一次引文校验，类似证据解析）；
   - 校验失败 → 不写入，退回结构场景。

**不做的事**：不把摘要写进 Git 账本作为记忆。它存在 `runtime.json` 里，随时可删可重算。用户的「接受/编辑/历史版本」那套流程仍然只作用于原子记忆。

### 注入时的优先级

场景摘要**不替代**原子记忆注入。理由：原子记忆带证据、可归因；摘要不带。所以注入永远只注入原子记忆，场景只影响**排序权重**（同一场景内被多条命中的原子，优先级上调）。

## L3 人设：一个可以重建的缓存

人设 = 对「长期稳定的偏好、约定、决策」的归纳。

### 生成规则

- 输入：所有 `status === "active"`、且 `type ∈ {preference, instruction, decision}` 的原子记忆；
- 按 `type` + 实体聚类，同一主题下 ≥2 条才归纳成一行；
- 每一行必须带 `sources: [memoryId...]`，界面上可点开看原文；
- 输出只读缓存，存在 `runtime.json`，带 `version`（账本 head）标记。

### 关键约束

| 约束 | 原因 |
|---|---|
| 每一行必须有 ≥1 条来源 | 没有来源的画像就是刻板印象 |
| 原子记忆变动 → 人设版本失效，下次访问重算 | 避免「改了记忆但画像还是旧的」 |
| 用户可以固定（pin）或隐藏某一行 | 归纳错了要有明确的纠正入口 |
| 人设不能反向修改原子记忆 | 视图不能篡改事实 |
| 人设内容不参与注入 | 注入只给原话，不给归纳 |

### 为什么人设不参与注入

一个反直觉但重要的决定。人设看起来最适合注入（短、概括），但它有两个致命缺陷：

1. **不可追溯**：模型看到「用户偏好简洁」，无法回到底层证据，容易在无关话题上过度套用；
2. **自我强化**：一旦人设进了上下文，模型后续行为都在验证这份画像，错误会累积。

所以注入只放原子记忆原话，人设只是给人看的、以及给「该提取什么」提供线索。

## 数据存放

```
~/.dsh/dsh-memory/
  ledger/            Git 账本：只有原子记忆 + 变更历史（唯一事实）
  runtime/
    runtime.json     候选、注入记录、场景视图、人设缓存
```

场景与人设放 `runtime.json`，与候选同一层。理由一致：**它们是可丢弃的派生数据，不该进 Git 历史**。误删只会导致下次重算，不会丢事实。

## 需要验证的前提

实现前必须先确认（重启后才能查）：

1. `ctx.get('llm')` 在 Host 里可用吗？（任务板用过 `llm` 服务解析任务，说明大概率可用）
2. 模型调用能否设置超时和失败降级？（不能的话自动摘要一律跳过，只做结构场景）
3. 一次会话里 LLM 调用会不会和 DSH 自己的模型调用抢配额或阻塞？（决定了要不要限流）

**预设**：如果不能确认 1 或 2，就只做结构场景 + 用户手写摘要，人设只做归纳展示不调模型。这样即使没有 LLM，L2/L3 依然有可用形态。
