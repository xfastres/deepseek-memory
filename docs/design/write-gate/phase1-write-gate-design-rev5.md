## 1. 本轮修订摘要

1. 认证失败、总开关关闭、缺批准、意图不匹配各自一个状态码。Rev.4 第 2 节与第 10 节不再互相矛盾。
2. 工作区干净且当前历史里没有 `idempotency_key`，**不能**断言原操作从未提交。写入前记下 HEAD；恢复时检查祖先关系；历史被重写或无法证明未提交时停止，交给人工。
3. 同一 `session_id#event_seq` 若引文或类型冲突，拒绝写入。不再按输入顺序留第一条。批准哈希与账本写入用同一函数。
4. ADD 要求正文出现在用户消息里，是 MVP 的可证明性约束，不是事实真伪判断。改写、归纳后对不上字面的句子不写成已核验事实。

## 2. HTTP 状态码（唯一表）

门禁顺序不变：先认证，再看总开关，再看批准与意图哈希，再看证据、基线、幂等。**[设计]**

| 情形 | 状态 | 错误码 | 账本 |
|---|---|---|---|
| 没有可用身份（无凭据、凭据无效、跨站、伪造 Host/Origin） | **401** | `unauthenticated` | 不写 |
| 身份存在但不是受信调用者 | **403** | `forbidden` | 不写 |
| 已认证，但 `writesEnabled=false` | **503** | `write-gate-not-ready` | 不写 |
| 已认证、总开关开，但没有批准也没有有效 PolicyGrant | **403** | `approval-required` | 不写 |
| 同一 `approval_id`，意图哈希与批准记录不同 | **409** | `approval-intent-mismatch` | 不写；不返回旧结果 |
| 认证服务本身不可用（不是“请求没带凭据”） | **503** | `caller-auth-unavailable` | 不写 |
| 工作区脏或历史关系无法证明 | **503** | `ledger-dirty` 或 `ledger-history-uncertain` | 不写 |

约定：

- **401 只表示认不出身份。** 不要用 503 表示认证失败。
- **403 表示已知道是谁，但不允许这次操作。** `forbidden` 与 `approval-required` 分开，避免把“不是受信调用者”和“是受信调用者但没批准”混成同一个错误。
- **503 只表示门禁或账本暂时不能安全写。** `writesEnabled=false` 的 503 仍然不证明 CallerAuth 正常；认证测试必须单独覆盖 401/403。
- Rev.4 第 10 节写的“认证失败也是 503”作废。阶段 1 失败姿态改为：认证失败返回 401/403；已认证但总开关关闭返回 503。两种都不降级成回环放行。

## 3. Git 恢复

### 3.1 已有代码事实

- `idempotency_key` 与 change 在同一次 commit。**[代码]** `ledger.js:348-386`
- 回执在 commit 之后，不进 Git。**[代码]** `:398-401`
- 工作区不等于 HEAD 时拒绝写入。**[代码]** `:234-241`

### 3.2 写入前必须记下的东西

批准进入 `consuming` 之前，记下：

- `pre_head`：当时 `git rev-parse HEAD`；空仓库记 `null`
- `intent_sha256`
- `idempotency_key`（等于 `approval_id`）

这三项写进批准记录。没有 `pre_head` 的旧 `consuming` 记录，恢复时不得退回 `granted`。

### 3.3 恢复判定

先看工作区，再看祖先关系，最后才搜键。

| 条件 | 动作 |
|---|---|
| `git status --porcelain` 非空 | 停止写入，503 `ledger-dirty`。批准保持 `consuming`。不执行 reset/clean |
| 读不到 Git，或没有记下 `pre_head` | 停止，503 `ledger-history-uncertain`。不退回 `granted` |
| 当前 HEAD **不是** `pre_head` 的后裔（`merge-base --is-ancestor` 失败：reset 到祖先、换仓库、历史被重写） | 停止，503 `ledger-history-uncertain`。批准标 `needs-manual`。**不得**因为当前历史里没有这个键就当成没提交过 |
| 当前 HEAD 是 `pre_head` 的后裔（或相等），且从 `pre_head` 到 HEAD 的提交里能找到该键 | 已提交。补回执，批准标 `consumed` |
| 当前 HEAD 是 `pre_head` 的后裔，工作区干净，这段历史里确实没有该键 | 可以退回 `granted`（未过期）或 `failed`（已过期） |

`pre_head` 为 `null`（写入前没有 commit）时：只有当前仓库仍是同一个、工作区干净、且全部可达历史都搜过仍没有该键，才能退回 `granted`。若 HEAD 存在但无法确认它从空仓库连续长出来，按历史不确定处理。

### 3.4 人工恢复

自动对账不得：

- `git reset`、`git clean`、删未提交文件
- 在无法证明“没提交过”时把批准改回 `granted` 并再写一次

人工处理只能二选一，并且要留下操作者与理由：

1. 指出已存在的 `change_id`，把批准标成 `consumed`；或
2. 确认这次变更不应再写，把批准标成 `revoked`。若仍要写，必须新签一个批准，不复用旧 `approval_id`。

对账可重复跑：已 `consumed` / `needs-manual` / `revoked` 的记录不改状态；脏工作区每次仍停止，不改脏状态。

## 4. source_refs 决定性

账本现有 `dedupeRefs` 只用 `session_id#event_seq` 当键，同键留第一条。**[代码]** `ledger.js:450-457`。若两条引用的 `quote_sha256` 或 `event_type` 不同，结果取决于输入顺序。这不能用于批准哈希。

设计：新增一个函数 `normalizeSourceRefs`，批准哈希和账本写入都调它，不再各自去重。

1. 字段完全相同（`session_id`、`event_seq`、`event_type`、`quote_sha256`）：只留一条。
2. 同一 `session_id` 与 `event_seq`，但 `event_type` 或 `quote_sha256` 不同（含一条有哈希、一条没有）：**拒绝**，422 `evidence-conflict`。不选第一条，不写账本。
3. 不冲突的引用再按 `(session_id, event_seq)` 升序。
4. 冲突时哈希函数抛错，不产生可能与账本不同的哈希。

## 5. ADD 正文匹配的含义

**[设计]** 正文必须出现在对应用户消息里，是 MVP 的产品约束，用来保证“这句话能指回用户原话”。它**不是**事实真伪判断。

| 情形 | 行为 |
|---|---|
| 正文与用户消息一致，或去掉首尾空白后是其子串 | 可以作为 ADD 的新证据 |
| 语义相同，但经过归纳、改写、翻译，字面对不上 | **拒绝写成已核验的正式记忆**。422 `evidence-not-literal`。可以留在候选或提案，等用户单独批准；批准后仍记 `fact_reverified:false`，除非用户提供了能对上的新引文 |
| 字面匹配成功 | 只表示“这段字出现在用户消息里”。不表示这件事为真、仍然有效或适用于当前项目 |

账本与注入文案不得把“正文匹配通过”写成“事实已核验”。用“能指回用户原话”。

## 7. 仍然存在的风险

- V1–V11 仍然全部未执行。`connection` 认证是契约，不是已验证的运行行为。
- 同用户进程仍可能读走浏览器凭据或 `policy.key`。
- V4/A8 未过前，正式写入保持关闭；面板弱批准仍未被批准为可开启。
- 字面匹配会漏掉真实但被改写过的偏好，也会放过用户随口说、并非仍然成立的句子。
- 脏工作区或历史不确定会一直挡住写入，直到人工处理。
- 若 `pre_head` 未写入就崩溃，该次批准只能走人工路径，不能自动恢复。

待确认项与 Rev.4 相同，本稿不把它们当成已批准的决策：面板弱批准是否保留、UPDATE 是否允许沿用旧证据、强批准未证明前是否禁止打开 autoAccept、Provider 无人类批准时是否只返回 candidate。
